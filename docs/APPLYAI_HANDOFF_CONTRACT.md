# letsA(ppl)I → applyAI Role Handoff Contract

**Status:** Draft (not locked)
**Version:** handoff v1.0
**Systems:**

* **letsA(ppl)I** — this repo (`letsApplI`). Job discovery, hydration, interpretation, pipeline.
* **applyAI** — the `career_explorer` repo. Reflective conversation, consented memory, and (future) Phase 6 Applied Exploration.

**Builds on:**

* `docs/PHASE5_APPLYAI_INTEGRATION.md` (relationship and boundaries, design-locked)
* `docs/PHASE5_2_OUTPUT_CONTRACT.md` and `src/phase5/phase5_2/schema/phase_5_2_interpretation.schema.json` (source data)
* `career_explorer/docs/phase-roadmap.md` §5 "Path A — Goal Declared" and §7 "Memory Interaction Rule" (receiving use)
* `career_explorer/docs/phase5_4_memory_schema.md` and `docs/phase5_5_route_contracts.md` (receiving invariants)

---

## 0. Purpose

This contract defines the **only** way information moves between the two systems:

> **A user may hand one interpreted role from letsA(ppl)I to applyAI, so applyAI can help them design evidence-building projects for that role.**

That is the whole integration. Everything not described here is forbidden.

The guiding sentence for both sides:

> **letsA(ppl)I describes the role. applyAI helps the user describe and build their own evidence. Neither system ever compares the two.**

---

## 1. Shape of the Integration

```
letsA(ppl)I UI                     user's browser                      applyAI
──────────────                     ──────────────                      ───────
validated interpretation  ──►  user clicks "Explore in applyAI"
                               + confirms handoff preview      ──►  POST /explore/role
                                                                    validate envelope
                                                                    show role context (session only)
                                                                    Path A conversation
                                                                    (nothing stored unless the user
                                                                     approves a memory proposal)
```

Properties:

| Property | Rule |
|---|---|
| Direction | **One-way**: letsA(ppl)I → applyAI. There is no return path in v1. |
| Trigger | **User-initiated only.** One click plus one confirmation, per job, per handoff. |
| Transport | **Browser-mediated.** The user's browser submits the envelope to applyAI as an HTML form POST. The letsA(ppl)I backend never calls applyAI, and applyAI never calls letsA(ppl)I. |
| Granularity | **One job per handoff.** No batch export, no "send my whole pipeline". |
| Persistence | **None by default** on either side (see §6). |
| Default state | **Off.** Hidden unless both sides enable it (see §8). |

Why browser-mediated: it keeps the user physically in the loop, needs no
server-to-server credentials, needs no CORS changes to the bridge API, and
makes background or automatic transfer structurally impossible.

---

## 2. Preconditions (letsA(ppl)I side)

The handoff control may be shown **only if all** of these hold:

1. The job has a stored interpretation in `job_interpretations` that passed the
   Phase 5.2 validator pipeline (schema, grounding, language, actor).
2. That interpretation is not stale per `_is_cached_interpretation_stale`.
3. The user has not revoked interpretation consent for this job.
4. The handoff feature is enabled (see §8).

If any precondition fails, the control is not rendered. It is never rendered
disabled-with-a-nudge ("interpret this job to send it to applyAI"), because
that would pressure the user into interpretation.

## 3. The Handoff Envelope (v1.0)

### 3.1 Schema

```json
{
  "handoff_version": "1.0",
  "handoff_id": "uuid-v4, generated by letsA(ppl)I UI at confirm time",
  "source": {
    "system": "letsappli",
    "job_id": "string",
    "company": "string",
    "title": "string",
    "job_url": "https URL of the public posting",
    "interpretation_schema_version": "5.2.0",
    "interpreted_at": "ISO-8601"
  },
  "role": {
    "summary_text": "string (RoleSummary.summary_text)",
    "explicit_requirements": [
      { "requirement_text": "string", "modality": "required | preferred | optional" }
    ],
    "capability_emphasis": [
      { "domain_label": "string", "description": "string", "evidence": ["quoted posting text"] }
    ],
    "project_opportunities": [
      { "capability_surface": "string", "description": "string", "evidence": ["quoted posting text"] }
    ],
    "structural_notes": "string (InterpretationResult.structural_notes)",
    "confidence": "LOW | MEDIUM | HIGH"
  },
  "framing": "This describes what one job posting says. It says nothing about you."
}
```

### 3.2 Field mapping from Phase 5.2

| Envelope field | Phase 5.2 source | Transform |
|---|---|---|
| `role.summary_text` | `RoleSummary.summary_text` | verbatim |
| `role.explicit_requirements[]` | `RequirementsAnalysis.explicit_requirements[]` | drop `source_span_id` |
| `role.capability_emphasis[]` | `CapabilityEmphasisSignals[]` | resolve `evidence_span_ids` to quoted span text via the stored span map |
| `role.project_opportunities[]` | `ProjectOpportunitySignals[]` | same as above |
| `role.structural_notes` | `InterpretationResult.structural_notes` | verbatim |
| `role.confidence` | `confidence` | verbatim |

Span IDs are resolved to text because applyAI has no span map and must not
fetch the posting itself. Each quoted span is capped at 500 characters.

### 3.3 Explicitly excluded

The envelope must **never** contain:

* raw or hydrated job description HTML/text (only the quoted evidence spans above)
* `RequirementsAnalysis.implicit_signals` (inferred, not stated; stays in letsA(ppl)I)
* pipeline state: status, star, ignore/skip, applied, notes, timestamps of user actions
* discovery signals (`AI`, `DATA`, `BACKEND`, …) or feed priority (🔥 / 🟡 / 🧊)
* anything from `resume.txt`, `applied.txt`, or Phase 5.1 gap-surfacing output
* any `ResumeAlignment` field (`strength_matches`, `resume_gaps`, `suggested_resume_bullets`)
* user identifiers, emails, session IDs, consent records

### 3.4 Limits

* Max envelope size: 64 KB serialized.
* Max array lengths match the Phase 5.2 schema (≤7 capability, ≤7 project items).
* All strings are plain text. No HTML, no Markdown rendering on the receiving side.

## 4. Sending Rules (letsA(ppl)I)

1. **Preview before send.** On click, show the user the exact envelope content
   in readable form, plus the `framing` line, and a "Send to applyAI" confirm
   button. Cancel discards it.
2. **No side effects.** Sending must not change `job_user_state`, must not
   re-run interpretation, and must not write to any table.
3. **No record of the handoff.** letsA(ppl)I does not log or persist that a
   handoff happened (consistent with "no user behavior recorded").
4. **Build from stored, validated data only.** The envelope is assembled from
   the cached validated interpretation, never from a fresh LLM call.
5. **Opens in a new tab.** The form targets `_blank` so letsA(ppl)I state is
   untouched.

---

## 5. Receiving Rules (applyAI)

### 5.1 Route

`POST /explore/role` is a **new Phase 6 route** in `career_explorer/app.py`.
It needs its own entry in `docs/phase5_5_route_contracts.md` (or its Phase 6
successor) before implementation, per the Step 0 immutability lock.

### 5.2 Validation (reject on any failure)

* `handoff_version` major must be `1`; unknown majors are rejected.
* `source.system == "letsappli"`.
* Allowlisted keys only; unknown keys are rejected, not ignored.
* Size and length limits from §3.4.
* `job_url` must be `https://`.

Rejection shows a plain error page with the reason. No partial state is kept.

### 5.3 Use

* The envelope becomes **session-scoped role context** for a Path A
  conversation. It is held in memory only, keyed to the `ce_owner_id` owner,
  never written to disk, and gone on `/reset` or process restart.
  * Today `app.py` keeps conversation state in one process-wide
    `conversation_state` dict, not per owner. Role context must be keyed per
    owner from the start, so one user's role cannot show up in another's session.
* **Cookie handling.** The `ce_owner_id` cookie is not sent on a cross-site
  form POST under the default `SameSite=Lax` policy. `/explore/role` must
  therefore validate the envelope, park it under a single-use token with a
  short expiry (5 minutes), and answer `303` to `GET /explore/role/<token>`.
  The GET (a top-level navigation, so the cookie is sent) binds the role
  context to the owner and deletes the token. An expired or reused token
  shows "This handoff expired; send it again from letsA(ppl)I."
* The page shows a persistent banner with the `framing` text and the source
  (`company`, `title`, link to `job_url`).
* applyAI may use the role context to:
  * walk through the role's capabilities in the posting's own words
  * propose **project concepts** that would produce visible evidence of a
    capability, framed as exploration ("one way to show this would be…")
  * state tradeoffs and limits, including that no project guarantees an outcome
* applyAI must keep the role context and the user's reflections/memory
  **side by side, never merged.** Memory items enter the conversation only when
  the user selects them (roadmap §7), and any use is attributed ("using items
  you selected").

### 5.4 Memory

* The envelope itself is **never** stored as memory.
* Role content (capabilities, requirements, project ideas) is **never** turned
  into a memory proposal, because it is not user-authored.
* The only memory that may arise is a normal `MemoryProposal` of kind `GOAL`,
  with text the user writes or edits (for example, "I want to explore roles
  like Platform Engineer"), approved through the existing
  `/memory/proposals/<id>/approve` route.
* applyAI may log receipt as an internal event containing only
  `handoff_id` and a server-generated `received_at`. No payload content in logs.

### 5.5 Timestamps

`interpreted_at` is displayed as provenance only. applyAI generates its own
timestamps server-side and never uses client-supplied time for records.

---

## 6. Forbidden on Both Sides

Neither system may, at any time:

* compute or display fit, match, alignment, readiness, or gap scores between a
  user and a role
* say or imply "you'd be good at this", "you're ready", "you're missing X",
  or rank roles for the user
* use memory, reflections, or signals from applyAI to filter, rank, or
  prioritize jobs in letsA(ppl)I
* use the user's letsA(ppl)I pipeline to infer goals or traits in applyAI
* send handoffs automatically, in batches, or in the background
* change pipeline state as a result of anything in applyAI
* share data with any third party as part of this integration

---

## 7. Revocation and Forgetting

* There is no back channel, so revoking interpretation consent in letsA(ppl)I
  **cannot** reach an applyAI session that already received the role. The
  preview step (§4.1) must say so plainly.
* applyAI provides a "Clear role context" control that removes the envelope
  from the session immediately. `/reset` also clears it.
* A `GOAL` memory item approved from a handoff conversation is ordinary memory
  and is forgotten through the existing memory controls.

---

## 8. Enablement

Off by default on both sides.

* **letsA(ppl)I:** the control renders only when `VITE_APPLYAI_HANDOFF_URL` is
  set to the applyAI `/explore/role` URL.
* **applyAI:** `/explore/role` returns 404 unless Phase 6 is opened. Per
  `phase-roadmap.md` §10, that requires Phase 5.4 memory to be implemented,
  tested, and hardened first. This contract does not open Phase 6 by itself.

---

## 9. Required Tests

### letsA(ppl)I

* Control is absent when any §2 precondition fails.
* Envelope contains only allowlisted fields (snapshot test against a fixture
  interpretation).
* Excluded fields (§3.3) never appear, including with a fixture that has
  `implicit_signals`, pipeline state, and resume data present.
* Span IDs resolve to quoted text; missing spans abort envelope creation.
* Sending causes no DB writes (row counts unchanged across all tables).

### applyAI

* Unknown version, unknown key, oversize payload, non-https URL: each rejected
  with no session state left behind.
* Accepted envelope writes nothing to `memory.json` or proposals.
* Role content cannot be submitted as a memory proposal.
* "Clear role context" and `/reset` remove it from the session.
* Language guard: generated Path A text contains no fit/score/readiness phrases
  (reuse the Phase 5.3 phrase constraints).
* Log entry for receipt contains only `handoff_id` and `received_at`.

---

## 10. Versioning

* Additive, optional fields: minor bump (`1.1`). Receivers must still reject
  keys they do not know, so the receiver updates first.
* Any removal, rename, or meaning change: major bump (`2.0`) and a new
  contract revision.
* A return path (applyAI → letsA(ppl)I) is a major change and needs its own
  contract.

---

## 11. Open Questions

1. **Gap surfacing.** `PHASE5_APPLYAI_INTEGRATION.md` describes letsA(ppl)I
   surfacing *evidence gaps* against the resume and handing those off. This
   draft deliberately carries only the role, not gaps, because gaps are
   user-specific. Should gaps ever travel, and if so only as user-edited text?
2. **Return path.** applyAI's "portfolio of thinking"
   (`future_company_partnership_models.md`) could later let a user attach a
   finished project to a saved job. Out of scope for v1.
3. **Hosting.** applyAI currently runs locally only. The browser-mediated
   transport works with a local URL, but a hosted applyAI needs its own
   origin and CSRF decision for `/explore/role`.
4. **Naming.** "applyAI" and "letsA(ppl)I" are close. Decide whether they are
   one product with two modes or two products before any user-facing copy ships.
5. **Phase numbering.** Both repos use "Phase 5.x" with different meanings.
   This contract uses handoff versions instead, and should be cited by name,
   not phase number.
